# How this site is built

Jekyll skips folders that start with an underscore, so nothing in `_build/` is served.

1. `canvas/` holds the three design pages (`.dc.html`), the same files as the claude.ai Design canvas.
2. `node dump.js canvas vals.json` evaluates each page's `renderVals()` for every interactive state.
3. `python3 build.py canvas out vals.json` writes `index.html`, `local.html`, `mainframe.html`, `404.html`, `sitemap.xml`, `robots.txt`, `favicon.svg`, `CNAME`.
4. `python3 enhance.py out` adds what the canvas doesn't carry: the packed-decimal decoder (`comp3.html`), tap-a-number sources on the receipts, the raw-to-reel timeline, the intake quiz, drop-in hours, and stand-ins for the photo.
4b. The four free tools (`shotlist.html`, `captions.html`, `receipt.html`, `scaler.html`, added Nov 8, 2026) are written by `tools/`: `cd tools && python3 shotlist.py ..` (same for `captions.py`, `receipt.py`, `scaler.py`) regenerates the template in `_build/`, with the shared header and footer from `tools/chrome.py`. Edit the `.py` file, never the generated page. `enhance.py` copies them into `out/`, along with `assets/bird-league-then-now.jpg` for the Bird League card on `work.html`.
4c. Share cards (Nov 9, 2026): `python3 tools/og.py out` draws a 1200 by 630 PNG per public page into `assets/og/` from each finished page's `<h1>` and meta description, with the fonts in `assets/fonts/` (OFL). It reads the pages after steps 5 and 6, so rerun it after a build whenever a headline or description changes, then rebuild from step 4. `enhance.py` copies the cards to `out/og/` and adds the `og:image` and `twitter:card` tags (the four tools get theirs from `tools/chrome.py`). Copy `out/og/` to `og/` at the repo root along with the pages.
4d. The Studio (Nov 11, 2026): `cd tools && python3 studio.py ..` writes `studio.html` from `studio.json` (the products) and `shipped.json` (the build log, newest first), with the header and footer from `tools/chrome.py`. Every word comes from those two files. A product with a `gate` doesn't show, and neither do its log lines; log lines older than 120 days drop off; the count over the log is counted from the lines that show, as of the day `studio.py` runs. `enhance.py` copies the page in and adds "Studio" to every header (before "Free tools") except the three Mainframe pages (T-16). It stops the build if either JSON file changed since `studio.py` last ran.
   Product pages (T-09, Nov 11, 2026): `studio.py` also writes `studio-<id>.html` for each product with no gate and a join list (today `studio-birdleague.html` and `studio-deepcuts.html`): the product's name, status, what, proof, image, every log line of its own that shows, and one join box. Each card links to its page ("More on <name> →"), and each page links back ("← The Studio"). When a gate clears (the album), its page, sitemap line and share card appear on the next build: run `studio.py`, build, run `tools/og.py out`, then rebuild from step 4 so the new card is copied in.
   Join lists (T-10, Nov 11, 2026): every join button is a small form, an email field and the list's button. It posts `form: "list"` to the intake Worker (`worker/intake.js`, the same address as `start.html`), says "You're on the list" when the Worker answers ok, and otherwise opens the old mailto ("List: <product name>"). The line under a product page's box is the list's `line` in `studio.json`. After any change to `worker/intake.js`, make the same change in `worker/intake.deployed.js` (the one-line file Josef pastes into Cloudflare) and run `node worker/test_intake.mjs`, which checks both with no network.
   To log a ship: Claude adds one line at the top of `shipped.json` (`date`, `project`, `line`: plain words for a stranger, no client names), runs `studio.py`, rebuilds from step 2, tests, and commits. Josef never edits it. A line stays only if a stranger can picture what changed: no build number without what a person can now do. A new `project` needs a product in `studio.json` with the same `id` (its name becomes the line's label), or the build stops and names it. Rerun `studio.py` before any push, so the count and the 120-day drop-off are counted from that day.
4e. Website checkup (T-04, Nov 12, 2026): `cd tools && python3 checkup.py ..` writes `checkup.html`, the fifth free tool (work page card, the `local.html` tools section and every tool's "More free tools" line list it). The page asks the `dj-checkup` Worker (`worker/checkup.js`, separate from intake) to fetch an owner's page and answer with plain facts; the page turns them into the two report cards. `CHECKUP_URL` at the top of the page's script is empty until the Worker is live: while it is, the page says "Coming this week" and shows no box. When Josef pastes the Worker's address, set it, rerun `checkup.py`, rebuild and test. `node worker/test_checkup.mjs` checks the Worker's safety rules, link classifier and AI checks with no network (`test_new.py` runs it). The AI crawler names in `checkup.js` come from each company's own docs; reread them before changing the list.
5. `python3 plain.py out` runs the plain-language pass (Oct 26, 2026) over the finished pages. Every edit must hit at least once.
6. `python3 intent.py out` runs the intent pass (Oct 28, 2026): every word on a page is there on purpose for a specific reader. Each edit carries its line ID from the audit in the vault (`Claude outputs/2026-10-28-intent-audit-dragomans-journey.md`) and must match exactly, or nothing is written.
6a. `python3 voice2.py out` runs the voice pass (Nov 12, 2026), after `intent.py` and before `final.py`: Josef's own words, approved line by line; the record is in the vault at `Claude outputs/dragomans-journey/voice-pass-2026-11-12.md`. Each edit carries its ID (V1, V2, ...) and must match exactly once, or nothing is written and the build names the edit that missed. Later pages add their edits to this same file.
6b. `python3 final.py out` runs last, after `voice2.py` (Nov 11, 2026). It reads the finished pages and adds one `<script type="application/ld+json">` before `</head>` on `local.html` (the business, its offers and its FAQ) and `mainframe.html` (the Mainframe Route and its priced steps). Every name, price, description and FAQ line is read from the page, so it always matches what the page says; if a price can't be found, the build fails and names it. It isn't in `enhance.py` because `intent.py` counts exact matches, and a second copy of a page's words in a script tag would break that. `tools/og.py` is not affected: it reads only each page's `<h1>` and meta description, which `final.py` doesn't touch.
   The visit counter (T-12, Nov 11, 2026) lives here too: `CF_BEACON_TOKEN` at the top of `final.py`. While it is empty, nothing is added. When it holds the token from Cloudflare's Web Analytics snippet, `final.py` first adds one sentence to the `local.html` FAQ answer "What do you do with our data?" (so the FAQ data carries it too), then puts Cloudflare's beacon just before `</body>` on every page except `comp3.html` (its address holds pasted bytes on purpose). `start.html` clears its own `#` after reading it, so text typed on the quiz or the receipt never sits in the address the beacon can see.
7. Serve `out/` locally and run `test_site.py` and `test_new.py`. `test_new.py` also runs `node worker/test_intake.mjs`.

Settings at the top of `enhance.py`: `DROPIN_DATE`, `DROPIN_PLACE`, `LINKEDIN`. Fill them in and rebuild. Setting at the top of `final.py`: `CF_BEACON_TOKEN` (step 6b).

## Hosting

Today GitHub Pages serves the repository root. Cloudflare hosting is built but not switched on yet (T-15, Nov 12, 2026; the switch steps are in T-15's Receipt in `trip/QUEUE.md`).

- `sh _build/publish.sh` makes `dist/`, exactly the public site: every git-tracked file outside `_build/`, except `CNAME`, `wrangler.jsonc`, and any name starting with a dot or an underscore. It fails loudly if `dist/` would be empty or if anything from `_build/` lands in it. `dist/` is in `.gitignore`.
- It also writes `dist/_redirects`. Cloudflare reads that file and never serves it. The first line, `/ /index.html 200`, lets `/` find the home page. Then comes one line per page, like `/local /local.html 200`. GitHub Pages answers `/local` as well as `/local.html`, and these lines keep those short addresses working after the switch. A `200` line serves the page at the short address; it doesn't redirect. The lines are made from the git-tracked `.html` files at the root, so a new page gets its line on its own. `index.html` (the `/` line covers it) and `404.html` get none.
- `wrangler.jsonc` at the root: a Worker named `dragomans-journey` that serves `./dist` and runs no script. `html_handling` is `none`, so `/local.html` answers at that exact address instead of redirecting to `/local`. `not_found_handling` is `404-page`, so a missing address gets `404.html` with status 404. `"previews": {}` gives every branch other than `main` its own preview address. It holds no secret.
- To check it locally: `sh _build/publish.sh`, then `npx wrangler dev --port 8765`, then run `test_new.py` against `http://127.0.0.1:8765/`.
- Forms don't send from a preview address or from the Worker's own `workers.dev` address, because the intake Worker only accepts the real site's address. That's expected.
