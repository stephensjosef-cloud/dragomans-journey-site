§1

Translation is close to free in 2026, and a wrong migration costs what it always did

On February 23, 2026, an AI lab described Claude Code reading and translating COBOL, and IBM had its worst trading day since 2000.1 By then AWS was already offering its own mainframe transformation agent at no charge.2 Turning COBOL into Java stopped being the hard part.

What changed is how migrations fail. A hand migration usually broke where everyone could see it, in code that wouldn't compile. An AI migration compiles, passes the tests the AI wrote for itself, and can still drop a rule the business depends on. It can also add one nobody asked for, which is harder to spot (Exhibit B).

Every source has an opinion. The stored bytes settle it.

In a real mainframe estate the sources disagree. The source says one thing, the copybook suggests another, the JCL a third, and the production files show something else again, and the engineer who knew why retired a decade ago. A tool that quietly picks one version to believe hides the problem, so every disagreement goes into the ledger as a finding.

§2 From the public record

What two AIs got wrong in a banking program, and why a reviewer would have signed it

Two different AIs translated the same banking program with a one-line prompt and no hints. Both handled packed decimal, half-up rounding and the copybook layout correctly on the first pass. What remained were the failures that read as correct. All of it is published, with the code and prompts, so anyone can rerun it.6

The rule nobody asked for.

Asked to translate a monthly interest program, one AI added an accumulation into a year-to-date field that the original program never reads and never writes.

A dropped rule shows up when output goes missing. An added rule reads as correct, and is probably true somewhere else in the system, just not in this program.

The Equivalence Dossier, the document you hand the examiner

Every claim in it points to bytes you can produce again on demand. It's built to answer the questions examiners and model-risk teams already ask about software a machine helped write.

A note on guidance. U.S. model-risk guidance was rewritten in April 2026 and, for now, leaves generative AI out of scope.7 Until that's settled, the dossier follows what examiners already check for: testing, outcomes analysis, reproducibility and a named person at the gate.

Exactly which programs, copybooks, JCL and data are in scope, captured at a fixed point so every later claim refers to the same starting estate.

Where source, copybook, declarations and production bytes agree, and every place they don’t, with the bytes that settled it.

Every field whose meaning isn’t in the code, the reading chosen, the evidence for it, and the business owner who confirmed it by name.

The harness source and the input files it runs, including edge cases for packed decimal, rounding, sign handling, encoding and sort order.

Each difference between original and migrated output: the replayable input, both outputs, the cause, the fix and who approved it.

Model versions, prompts, configuration and rerun instructions, so your team can produce every result again without me.

Coverage limits and out-of-scope behavior, stated beside the claims rather than buried after them.

Named people, dated signatures, and the exact build each signature covers.

§5

What a harness does not prove.

  • Behavior on inputs that never appear in the test corpus. Coverage is reported, never implied.
  • What the business intended, where nobody alive can say. Those fields go in the ambiguity register with a named owner, not a guess.
  • Performance, capacity or batch-window timing. Those need their own tests, and the dossier says so.
  • Anything about systems outside the agreed scope.

Anyone who promises "100% equivalence" without this list is promising something no one can check.
